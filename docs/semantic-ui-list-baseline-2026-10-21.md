# 窗口列表 CPU 与生命周期基线

本文按日期追加历史测量。最新原生细分计时见末尾“v36 原生引擎阶段”；集合编辑对照见“集合结构编辑与字段热路径”，窗口协调另见“窗口顺序与 LIS 快路径（2026-10-23）”。开头表格保留首版单次运行值，不能直接与后续统计对照混算。

日期：2026-10-21。Windows，Rust 1.98.0；bench opt-level=3，沿用 workspace 的单 codegen unit 与 LTO。一次运行的本机观测值，未做统计采样，也没有与旧 Each 的同功能虚拟化实现比较，不能据此声明整体应用提速比例。

复现：在仓库根目录运行 `./scripts/check-semantic-ui.ps1 -Bench`。脚本将 Cargo home、target 和临时目录全部指向 `D:/BuildCache/glory-semantic-ui`，先用 cargo metadata 检查实际 target。原始基线输出位于该目录的 `list-benchmark.txt`。

## 测量范围

[virtual_list.rs](../crates/ui/benches/virtual_list.rs) 测量窗口计算、按索引取 key、行缓存增删与 LIS 排序。基线 host 仅记录生命周期，不构造 DOM、不运行响应式 Binding、不做引擎布局/绘制，也不分配全量业务数据。因此这是算法和控制流成本，不能转换为实际浏览器或手机帧率。

定高：24px 行高、600px 视口、前后各 4 行 overscan，20,000 次窗口更新。连续滚动每次前进一行；跳转场景跨越大量行，通常整个窗口都需要替换。

| 场景 | 总条数 | 总耗时 | 读取 key 总数 | 峰值挂载行 | 行高索引槽位 |
|---|---:|---:|---:|---:|---:|
| 连续滚动 | 1,000,000 | 33.282ms | 659,990 | 33 | 0 |
| 连续滚动 | 100,000,000 | 33.661ms | 659,990 | 33 | 0 |
| 跨段跳转 | 1,000,000 | 40.099ms | 659,996 | 33 | 0 |
| 跨段跳转 | 100,000,000 | 41.632ms | 659,996 | 33 | 0 |

连续滚动新建/销毁各 20,028 行；跳转新建/销毁各 659,996 行。每组完成 clear 后存活行为 0。条数扩大 100 倍时 key 访问数和峰值行数未增加；固定高度模式不建立全量索引。这支持窗口工作量与总条数解耦，但不代表用户的数据源本身没有存储成本。

变高：1,000,000 条预估 24px 的数据，Fenwick 索引初始化 2.668ms；100,000 次“单行测量更新 + prefix + window 查询”共 37.932ms。索引包含 2,000,000 个 f64，约 15.3MiB，不含分配器与容器开销。变高 splice 为 O(n)，单独暴露为数据变更操作，滚动路径不会调用。

## 已有正确性证据

`cargo test -p glory-style -p glory-render -p glory-ui`：19 个测试通过；同一组包的 fmt 检查与 clippy `--all-targets -- -D warnings` 通过。`cargo tree -p glory-ui --edges normal` 只显示 ui/render/style，不含 Web 或 GPU 依赖。

[windowed_list.rs](../crates/ui/tests/windowed_list.rs) 使用真实的语义参考解释器：百万条惰性数据，最多 33 行和一个根节点；跨近千个远距离窗口跳转后，节点与 ID 槽位仍不超过 34。滚动一行只创建/销毁各一行，保留 key 的 NodeId 不变，同一窗口与 revision 再次协调时不读取 key。

其他测试包含：500 次随机插入/删除/重排后的实际参考树顺序与身份；2000 次变高测量与朴素模型对照；测量和 prepend 的锚点恢复；删除锚点后的邻行策略；240 亿逻辑像素的分段坐标、首尾跳转与 1px 增量。

[contract.rs](../crates/render/tests/contract.rs) 验证暂停/恢复与永久销毁的区别、过期身份和事件隔离、查询水位、有限内容模型，以及 20,000 次创建销毁后只保留一个 ID 槽位的回收行为。

## 初始 CPU 基线的未验收范围

实际 Web DOM 数量与滚动；requestAnimationFrame 合并；ResizeObserver 与字体加载后的高度修正；输入法/焦点保持；异步行资源取消；键盘与无障碍导航；物理滚动段重定位的浏览器表现；SSR 接管与 Blitz/Android。

这些属于继续实施与平台验收，不能用上述内存测试替代。当前成果是新语义层和虚拟列表算法基础，尚未完成新 UI builder、runtime 与实际呈现后端的端到端接线。

## 后续 R2 公开组件证据

[list_widget.rs](../crates/ui/tests/list_widget.rs) 现在通过公开 `list(...)`、App 和真正的 Widget/Owner/Binding/事件接线验证：1 亿条源只访问当前窗口；200 次同 tick 滚动输入合并为最终窗口的一次提交；同窗口内后续像素滚动不访问 key、不提交节点 Patch。小数像素会多覆盖一行，因此上述 viewport/行高/overscan 的一般上限为 34 行，而表中按整行滚动的基线峰值是 33 行。

公开组件还验证了 10 亿条数据上的 240 亿逻辑像素、首尾跳转、1px 增量、分段 ScrollTo 确认无循环、key 重排复用、行任务取消，以及行工厂对全局来源创建的 map 归属当前行 Owner。参考场景的节点和槽位不超过 70，处理器为 2；清空后没有行任务或派生值遗留。

测试宿主只记录平台动作与更新语义节点，不产生像素。上表仍是较低层 CPU 基线，没有测量新公开组件的浏览器帧率。变高测量、prepend key 锚点、焦点/键盘/无障碍及真实 Web/Blitz/设备验收继续按[实施记录](semantic-ui-implementation.md)推进。

## 变高组件与稀疏索引补充

`list(...).measure(24.0).measure_limit(64)` 已接真实行测量。Windows Chromium 155、1 亿条索引源、80 次远跳：最多 28 个行实例，64 条高度缓存，164 个稀疏节点/数值条目，实际预留容量峰值 614 个条目；UI 节点 ID arena 最多 105 槽，响应式 arena 最多 183 槽。已验证行高增长、稳定 key prepend、锚点删除、CSS transform、滚动条视口变化、超大单行及卸载。具体数字是单次观测，上限断言与场景见 [adaptive-acceptance.js](../examples/semantic-web/adaptive-acceptance.js)。

未知或淘汰高度回到估值，精确全表高度不是这个有限缓存的承诺。稀疏模型初始无需百万/亿级数组；单次测量和偏移定位使用稀疏 Fenwick，期望 O(log n)，而高度缓存按显式上限和当前窗口保护。原表的密集模型 CPU 基线保持原测量范围，本次没有给稀疏组件制造 FPS 推断。后续仍需性能时间分解、焦点/键盘/无障碍与原生设备验收。

## 异步行资源补充（2026-10-22）

公开 `Owner::resource` 现已接 Web 宿主。`resource-acceptance.js` 在同一 1 亿行惰性源上，为每个挂载行创建等待中的异步 future，再执行 80 次远距离滚动：最多 15 行/15 个请求、136 个响应式图槽、34 个语义节点。离屏行销毁后请求取消且从测试 I/O 注册表删除，不保留所有访问历史。全程 1137 个 future，2 个完成、1135 个取消；卸载后待处理 job、任务、图和 DOM 为 0。验收同时覆盖参数变化的旧请求不能完成、新结果由 RAF 自行呈现、失败/刷新/取消与显式种子。

这是实际浏览器中的任务生命周期与有界数量证据，使用可控制完成的本地异步 I/O；没有测量网络吞吐、远端请求取消、layout/paint/FPS。完整场景与 API 语义见[实施记录](semantic-ui-implementation.md)。

后续命名快照注册表接入同一回归：行以 `row/{key}` bind，80 次远跳的活跃注册数始终等于当前行数，最多 15；卸载后即便测试仍保留 Resources context 的 clone，注册数也为 0。未因增加资源序列化而保存所有访问历史，图槽峰值仍为 136。普通 SSR 资源快照验证另见 `resource-snapshot-acceptance.js`；这不改变性能计时与 FPS 的未验收范围。

## 异常窗口行预算（2026-10-22）

公开 List::row_limit 默认为 4096（含 overscan，焦点 pin 最多额外一行），初始按实际位置计算并在源 key/行工厂前拒绝。模型测试覆盖 1 亿行、极小行高、usize::MAX overscan 及极大视口：超限不分配 UI 节点或响应式图，不访问 key，不运行行工厂；尾部实际小窗口仍允许通过。

真实浏览器 budget-acceptance.js 使用 1 亿行、240px 视口，随后把根高度变为 100 万 px。定高/变高请求 35717/35718 行，返回 RowLimit(limit=4096)；没有新增行工厂，实际 DOM 行和任务为 0，外层只剩 4 个语义节点。source 最大查询下标仍为 10/11，没有查询扩大窗口；变高失败前可校验旧测量。恢复 240px 后回到 11/12 行和任务，End 继续抵达第 1 亿行；全部 Owner 创建/释放为 33/33、36/36。

ListStats inspection 保留上次成功值，错误场景的实际回收必须看 DOM/任务，不能误读旧 rows。预算只限制虚拟窗口行数，不限制单行子树资源或 ordinary Each，不承诺所有 OOM 可恢复。九组浏览器最终结果与精确范围见[实施记录](semantic-ui-implementation.md)；原 CPU 时间表不变，没有新增帧率结论。

有界暂留，entries≤2*queued+64，queued归零则entries归零。压缩仍保留阶段
优先级和活FIFO，不持有行/closure。capacity按阶段峰值复用，不当成RSS。
source/derived跳过队列查找，无废弃ID时不计算压缩条件。

5项core队列回归覆盖捕获即时释放、5,000次退休历史、代次/FIFO、drain时
界限和自我重排后退休。新增实际App/List/Memory回归：一亿逻辑行，在16,384
待绑定背景远跳，15次新key读取、压缩检查身份数0，旧行退出且活绑定顺序正确。
